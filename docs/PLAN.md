# 第一部分：序章《停電的二十分鐘》（2026-10-07）

## 目標與完成標準
照 `docs/SPEC.md` 做出四頁純靜態推理遊戲，GitHub Pages 可以直接發布。以下全部成立才算完成：
- `npm run check` 綠：內容隔離、明文答案掃描、判定窮舉、外部圖片掃描。
- `npm run e2e` 綠：手機直式（390×844）用真點擊跑完四頁，每件物品、每段口供都逐字核對；指控的五種結果都跑到；每頁沒有水平捲動。桌機寬（1280）抽查。
- README 寫好 Pages 部署步驟與邏輯問題（劇透折疊）。
- 在分支 commit、push、開 PR。

## 非目標
- 不改案件內容、不加線索；中性物品也照原文。
- 不做後端、帳號、兩機同步、計分或排行。
- 不引入框架或打包工具。

## 實作約定
- 只用 classic `<script>`，不用 ES module，因為 `file://` 開啟時 module 會被擋。各頁的案件內容寫在該頁 HTML 或該頁專屬的 JS；共用檔只放樣式與工具函式。
- 判定（建議做法，可以改，但紅線不能破）：
  - 每位嫌疑人一筆資料，用 `SHA-256(鹽|suspect|ID)` 當索引。每筆存一段 AES-GCM 密文，金鑰由同一個 ID 推導；解開後是 `{種類: 兇手或錯誤, 訊息}`。四筆格式一樣，光看原始碼分不出誰是兇手。
  - 選中兇手後，再把「嫌疑人＋證據＋破綻」一起雜湊，和「全對」雜湊清單比對（每件可接受證據 × 每句可接受破綻各一筆；目前 3 件 × 2 句，清單有六筆）。
  - 真相的金鑰由「嫌疑人＋破綻」推導，每句可接受的破綻各加密一份，所有全對組合都解得開。
  - 鹽、雜湊、密文由 `tools/build-secrets.mjs` 從 `tools/secrets.local.json` 產生，寫到 `js/secrets.js`。
- 選項 ID（嫌疑人、物品、口供句）產生機密檔後就不能改；要改得重產 `js/secrets.js`，而重產需要機密原文。
- 口供破綻下拉選單：依嫌疑人分組，一句一個選項，追問的回答也算口供；觀察反應不算口供。證據下拉選單：依房間分組，只列物品名稱，不列描述。
- `crypto.subtle` 只在安全環境可用（https、localhost）。用區網 IP 的 http 開啟會失效，accuse 頁要偵測到並提示改用 Pages 網址。
- 字體可以用 Google Fonts，但要寫系統字體 fallback；雲端網路可能擋字體，測試不能依賴字體載入。
- Pages 用 Jekyll 建置：`_config.yml` 的 exclude 會擋掉 docs/、tools/、測試等。HTML 不要加 YAML front matter，也不要加 `.nojekyll`（加了會把 docs/ 一起發布）。新增不該發布的資料夾時，記得補進 exclude。
- 可選的體驗細節（不改案件）：已看過的物品或已追問的卡片做標記（localStorage，讀寫包 try/catch）；accuse 頁開表單前加一句「兩人都準備好了嗎？」。

## 階段
0. **開工**：把使用者貼的機密段整理成 `tools/secrets.local.json`，附 `tools/secrets.example.json`（只放佔位字）。
   驗證：`git check-ignore -v tools/secrets.local.json` 有輸出，`git status` 看不到這個檔。
1. **共用樣式＋首頁**：`css/style.css`、`index.html`（標題、前言、兩個角色按鈕、規則、底部指控入口）。
   驗證：手機寬截圖；沒有水平捲動。
2. **scene.html**：可點的房間平面圖（inline SVG）加上房間分頁；點物品看描述；盆栽要按「翻開泥土」才出現埋著的蠟燭。
   驗證：e2e 逐一點開 10 件物品，文字和 SPEC 逐字相同。
3. **interrogation.html**：四張嫌疑人卡；按「追問」顯示問題、回答與斜體的觀察反應。陳先生在規格裡沒有觀察反應，那一欄就不顯示，也不補寫。
   驗證：e2e 逐字核對。
4. **判定核心**：`tools/build-secrets.mjs` 產生 `js/secrets.js`；`js/verdict.js` 負責雜湊比對與解密。
   驗證：node 窮舉 4×10×12 種組合，應該剛好一人走兇手路徑、全對組合剛好是「可接受證據 × 可接受破綻」的完整組合、其他三人不論選什麼證據都回自己的訊息。另外把解密結果和 `secrets.local.json` 逐字比對；這支腳本可以進 repo，讀不到檔案時要略過並提示。
5. **accuse.html**：三個欄位、判定訊息、全對時的破案動畫與真相。
   驗證：e2e 用真點擊跑全對（每組正確組合各一次）、兇手對但證據錯、兇手對但破綻錯、選錯三位嫌疑人。測試不能寫死正解：先用 node 窮舉 verdict 找出全對組合，再用真點擊選它。
6. **全站檢查 `npm run check`**：
   - 內容隔離：從 interrogation.html 取出每段口供文字，scene.html 和它載入的檔案裡都不能出現；反過來也一樣。
   - 明文掃描：用窮舉解密出的所有機密字串（取 6 字以上片段），掃描所有會發布的檔案。
   - `tools/secrets.local.json` 沒被 git 追蹤。
   - 沒有外部圖片。

   驗證：做負向案例。故意在 scene.html 放一句口供、在任一頁放一段真相，確認 check 會紅，再復原。
7. **README＋交付**：Pages 部署步驟（Settings → Pages → Deploy from a branch → main、/(root)；免費方案要 public repo）、怎麼玩、檔案結構、規格解讀（例如設計註記不顯示）、邏輯問題（用 `<details>` 劇透折疊，自己的話描述，不貼機密原文）。然後 commit、push、開 PR。

## 風險與回退
- **機密原文外洩**是最大風險。commit 前跑 `npm run check`，再 `git grep` 抽查幾個機密片段。萬一已經 push，先告訴使用者，不要自己改寫歷史。
- 雲端沒有機密段（使用者沒貼）：只做階段 1–3 和 accuse 的表單，判定等使用者貼。
- 外觀只能靠截圖判斷，所以每頁都要有手機截圖（放 output/），交付時附上。

## 使用者已拍板的決定（紅線）
- 2026-09-25 的規格全文（`docs/SPEC.md` 加上機密段）：不改案件內容，邏輯矛盾寫進 README。
- 2026-10-07：放到 GitHub 私人 repo，由雲端 Claude Code 實作（使用者的電腦要跑其他任務）。
- 2026-10-07：口供破綻改為接受兩句（是哪兩句屬機密段），機密檔用 `flaws` 陣列。原因寫在 README 劇透區的邏輯問題第 1 點。使用者桌面的開工檔要同步改，否則下次重產會變回一句。

## 決策：機密段不進 repo（2026-10-07）
- **背景**：規格要求原始碼不得有明文答案。但判定訊息與真相解說本身就會洩漏答案（例如真相寫明誰拿走懷錶；只有三人有「選錯訊息」也等於指出兇手），而且 repo 開 Pages 時可能要改成 public。
- **選項**：A 規格全文進 repo，最省事，但 public 後任何人都看得到答案。B 機密段由使用者在開工時貼給 session，repo 裡只放加密結果，代價是每次重產機密檔都要重貼。
- **決定**：選 B。原文只存在使用者桌面的 `停電的二十分鐘_雲端開工.md`（本機）和 session 內 gitignored 的 `tools/secrets.local.json`。
- **代價**：雲端 session 結束後機密原文就不在了；之後要改判定或真相，得請使用者重貼。
- **何時重新檢視**：使用者決定 repo 永遠私人（並用付費方案開 Pages）時，可以改回 A。

# 第二部分：懷錶檔案的新章節（2026-10-14）

## 背景與使用者的決定
- 使用者玩完序章，覺得太簡單，要求參考其他解謎遊戲，做出更有挑戰性的遊戲和更多章節。
- 2026-10-14 使用者拍板（AskUserQuestion）：
  1. **使用者自己也要玩**：不能劇透。答案只以加密形式進 repo，另外提供封存備份；使用者只看無劇透的章節簡介和測試結果。
  2. **同一個遊戲**：停電變成序章，首頁改成章節選單，加三章，最後一章是串起前面線索的終章。網址不變。
  3. **延續同一個世界**。
  4. **難度來源是「兩人資訊互鎖」**：偵訊官可以出示證物逼出改口；密碼鎖的線索和鎖分在兩支手機上。
- 目標：做出好玩、公平、有挑戰性的作品。

## 目標與完成標準
- 選單、序章、三章都能在手機直式用真點擊玩完：用通行碼解鎖章節、開密碼鎖、出示證物、指控的各種結果與破案。e2e 用兩個瀏覽器分別扮演兩支手機。
- `npm run check` 綠：
  - 只用已發布的檔案，從序章一路窮舉破到終章；
  - 每道鎖只有一組密碼；
  - 只有正解能破案，全對組合剛好是各格可接受答案的完整組合；
  - 解密後角色隔離；
  - 所有章節的明文掃描；
  - 原始內容沒進 git；
  - 封存檔解得開，而且和原始內容一致。
- 每章都由只看得到玩家畫面的 AI 試玩過（不准讀檔），確認推得出唯一解、沒有只能靠猜的格子。發現的問題都修掉。
- 文件、commit、PR 都沒有劇透。

## 架構
- **選單** `index.html`＋`js/menu.js`＋`chapters.js`：
  - `chapters.js` 只放各章的標題、一句話簡介、鹽，以及一個用通行碼才解得開的驗證密文。
  - 輸入通行碼後，先用驗證密文確認，再存進 localStorage（前綴 `blackout20:`）。
- **章節頁** `chN/{index,scene,interrogation,accuse}.html`：
  - 頁面外殼由 `tools/build-chapters.mjs` 產生，沒有任何案件內容。
  - 每頁載入 `js/case.js`、自己的 `*.data.js`、`js/case-<頁>.js`。
  - `*.data.js` 是 `{v, chapter, role, salt, box}`；`box` 用 `SHA-256(blackout20|chapter|章|鹽|通行碼)` 當 AES-GCM 金鑰。
- **解開之後還有第二層**：
  - **密碼鎖**：鎖住的物品用 `lock|鹽|編號|密碼` 推導金鑰；索引是 `lockidx|…` 的雜湊。
  - **改口**：用 `present|鹽|人物|證物編號` 推導金鑰；同一段改口可以由多件證物觸發，內容帶 id，頁面不重複顯示。
    - **反應**（`react`）：證物有關但對方不改口，只顯示一句話和觀察，不扣信用。
    - **連鎖改口**（`requires`）：要先逼出哪幾段，這段才會說；沒達成時不扣信用，卡片上記一則跟一般「反應」一模一樣的反應（`early`／`earlyBy` 都寫成 `{ say, observe }`），出示紀錄也寫「有反應」，之後可以再出示。這樣玩家分不出哪些證物之後會讓對方改口（2026-10-14 雙人試玩發現舊的「先從別的地方突破，再拿這件回來」等於直接告訴玩家答案）。暗示可以依「還缺哪一段」各寫一句（`earlyBy`），沒寫的就用 `early`。前置條件也在密文裡，看原始碼看不出哪些證物有關。
  - **指控**：
    - 第一格一定是人物，每個人的判定訊息各一筆，補成一樣長；
    - 全對時比對 `full|鹽|序列化答案` 的雜湊清單，真相用同一串推導金鑰；
    - 只錯一格時比對 `near|…`，回「只差一處」。
- **結案**：真相、尾聲與下一章通行碼都在真相密文裡，破案後才看得到。
- **原始內容** `tools/chapters.local/chN.json`（gitignored）：
  - 結構由 `tools/lib/chapters.mjs` 的 `validate` 檢查。
  - `build:chapters` 產生全部檔案後，立刻用通行碼解開、窮舉，再和原始內容比對。

## 實作約定
- 引擎（`js/case*.js`、`css/style.css`、`js/menu.js`）完全由資料驅動，不寫任何章節的內容或人物名字。
- 證物編號 `No.` 跨全章唯一；口供編號 `#` 跨全章唯一，追問與改口也有編號。指控用編號作答。
- 角色隔離在寫內容時就要注意：同一件事如果同時出現在物品描述和口供裡，要換句話說；check 用 6 字窗口比對。
- 指控欄位的提示文字（hint）屬於介面說明，不算劇透文字，但不能透露答案。
- 錯誤的出示會扣信用；同一組錯的組合不重複扣。合理但不關鍵的出示給「反應」，不扣信用，避免懲罰合理的推理。信用、提示、指控次數只影響破案評等，不擋進度。
- 口供編號：開場口供與追問依人物順序編號，改口的編號打散，缺號只告訴玩家「還有話沒說」，不透露是誰。
- 加難的原則（第一輪 AI 試玩後）：
  - 證物不直接寫名字；身分要靠兩支手機的資訊拼出來。
  - 密碼鎖要「規則在一邊、資料在另一邊」，而且要多一步推理，例如換算年份、鏡像、從好幾個候選裡挑。
  - 指控欄位問推理的結果（時刻、路線、怎麼知道的），不問一眼就認得出來的東西；選項不能洩題。
  - 每個不是兇手的人，都要有自己的秘密和可疑之處。
- 進度存在各自手機的 localStorage：
  - 通行碼、已查看、已開的鎖、已出示的證物、已看的提示、結案檔案；
  - 讀寫都包 try/catch，讀不到時頁面照樣能用。

## 驗證
- `npm run check`：新章節的部分不需要原始內容也能跑完一路破關，因為窮舉只用已發布的檔案；有 `tools/chapters.local/` 時再和原始內容比對。
- `npm run e2e`：
  - 兩個瀏覽器分別扮演兩支手機，從序章破案拿到通行碼，一路玩到終章；
  - 中間跑過錯誤通行碼、小寫加連字號的通行碼、所有密碼鎖、所有改口、一次錯誤出示；
  - 指控跑過選錯人、只錯一格、錯兩格、全對；
  - 檢查兩支手機的畫面互相看不到對方的內容。
- **AI 試玩**（第一輪三章都只有 4/10；第二輪起改成兩種能力的模型各玩一次）：
  - 用 scratchpad 裡的文字版介面，只呈現玩家畫面；不進 repo，因為它會讀原始內容的目錄位置。
  - 規則是不准讀檔、每道鎖最多試三次、指控只交一次。
  - 試玩回報的問題會修進原始內容，重新 build、封存、驗證。
- **雙人模擬試玩**（2026-10-14 起）：
  - 每章兩個互不相通的 AI，一個只能用現場的指令、一個只能用偵訊的指令；回合制，雙方交出【給搭檔的話】（每則 300 字以內）後由主控互相轉達，直到兩人同意同一份指控。
  - 第一輪發現的漏洞，也是之後寫新內容時的檢查清單：
    - 「還沒到時候」的出示不能看起來跟一般反應不同；
    - 表單題目和選項不能點破詭計，也不能點名要查誰；
    - 關鍵事實不要放在開場口供，改成出示或連鎖才問得出來；
    - 物證不能一眼就單獨鎖定兇手，要有站得住腳的誘餌；
    - 每個人對證物的反應數量要差不多，免得從反應多寡猜出兇手；
    - 鎖的密碼由來要拿鎖著的東西去問對的人；
    - 共用文字（簡報說明、表單、判定訊息）不能用代名詞透露兇手性別；
    - 合理的出示要給反應，不扣信用。
  - 改完由全新的玩家再玩一輪：三章都答對，5–6 回合，自評難度 6–7、好玩 8–9。

## 決策：新章節的原始內容怎麼保存（2026-10-14）
- **背景**：
  - 新章節是 Claude 寫的，不是使用者給的。
  - 雲端 session 結束後，gitignored 的原始內容就不在了。但之後要修改章節，一定需要原始內容。
  - 使用者自己也要玩，不能讓使用者在 repo 或對話裡看到劇透。
- **選項**：
  - A. 原始內容明文進 repo：最省事，但使用者和任何看得到 repo 的人都會被劇透。
  - B. 只進加密資料，原始內容丟掉：改章節就得從加密資料反推，很麻煩。
  - C. 原始內容用通關密語加密封存進 repo，通關密語交給使用者。
- **決定**：選 C。
  - `tools/chapters.sealed.json` 用 PBKDF2-SHA256（60 萬次）推導金鑰、AES-GCM 加密。
  - 通關密語只在使用者手上；開工時給 session，就能還原。
  - 序章的機密原文仍然照第一部分的決策處理，不放進封存檔。
- **代價**：通關密語遺失就只能從已發布的資料反推內容。check 會在提供通關密語時確認封存檔是最新的。
